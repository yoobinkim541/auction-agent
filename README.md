# gyeongmae-agent — 경매 매물 권리분석·입지분석 에이전트 (개인 투자용)

부동산 경매 매물을 크롤링해 **조건에 맞는 매물을 선별**하고, 법률데이터에 grounding된
Claude 에이전트가 **권리분석(말소기준권리·인수/소멸·임차인 대항력)** 과 **입지분석(시세·안전마진·교통·학군)** 을
수행하여 **웹 대시보드**와 **매일 아침 텔레그램 다이제스트**로 점수화된 매물을 보여준다.

목표는 **발품 절감** — "대시보드를 뒤지는" 일을 "아침에 추천 N건을 읽는" 일로 바꾼다.

> ⚠️ **면책**: 본 도구의 분석은 **참고용 정보**이며 법률자문이 아니다. 정확성을 보장하지 않으며 최종 판단·책임은 이용자에게 있다.
> 입찰 전 반드시 등기부등본·매각물건명세서·현장 확인 및 변호사/법무사 상담을 권장한다. 개인 이용 전용.

## 발품 절감 기능

| 기능 | 설명 |
|---|---|
| **경쟁 신호** | 법원경매 **관심물건 등록수**를 점수에 반영 — *남들이 덜 본 저경쟁·고마진 딜*을 위로 올림(🔥저경쟁, 정렬 "저경쟁순") |
| **사건 그룹핑** | 한 사건의 여러 물건을 대표 1건 + "외 N물건"으로 접어 검토 횟수↓(🗂 사건묶기) |
| **특수권리 하드제외** | 유치권·지분·법정지상권 등 위험 레드플래그를 통과에서 자동 제외(기본 ON, 조정 가능) |
| **AI 투자 의견서** | 통과 상위 N건에 권리·입지·수익·리스크 종합 + 보수적 입찰가/임장 포인트(Claude **구독 CLI**, 종량제 회피) |
| **일일 다이제스트** | 매일 06:00 KST 분석 후 통과 상위 N건을 텔레그램으로 발송(점수·진짜마진·위험·🔥저경쟁·원본링크) |
| **낙찰가 예측 밴드** | 수집한 실제 낙찰결과로 같은 시군구·유형의 낙찰가율 분포 → 📈 예상낙찰 밴드 + 🎯 입찰가 가이드(승률 50/70/90% 가격) — 입찰가 사례조사 발품 대체 |
| **관심물건 변동 알림** | ★매물의 기일 변경·유찰·최저가 하락·매각·문서(명세서) 갱신·🔥관심 급증을 diff해 변동 시에만 즉시 텔레그램(`watch:favs`) |
| **D-1 입찰 준비** | 내일 기일 매물의 보증금(10%)·법원·딥링크·준비물을 저녁에 자동 발송(`bid:prep`, 20:00 타이머) |
| **임장 코스** | 이번 주 후보를 시군구 클러스터+최근접 순서로 묶어 카카오맵 링크와 함께 — 봇 `/route`(=`/임장`) |
| **봇 원격 조작** | `/fav 사건번호` ★토글, `/case` 응답의 ★버튼(인라인), `/update` 원클릭 배포(`deploy/update.sh`) |
| **정밀 추천 인박스** | 데이터 신뢰·권리·점유·보수적 가치·절대 입찰상한을 모두 통과한 사건만 주 7건 이하로 노출. 0건이면 기준을 완화하지 않고 보강 사유를 안내 |
| **판단 저널** | 검토·관심·보류·임장·입찰검토·제외 결정을 사유·메모·목표 입찰가와 함께 append-only로 저장해 복기 데이터로 축적 |

## 구조

```
crawler/         법원경매(courtauction.go.kr, 메인)·더낙찰옥션(보조) 크롤러
  adapters/      사이트별 어댑터 (courtauction는 WebSquare dma_ API + 매각물건명세서 파싱)
  normalize.ts   한국어 금액/날짜/물건종류/권리종류 파싱 (순수함수, 테스트됨)
pipeline/
  rights/        권리분석 결정형 rule engine + 소액임차인 표 + Claude 2차 검증(CLI)
  location/      입지분석: 카카오 지오코딩·국토부 실거래가·POI·취득비용
  select/        진짜안전마진 + 인수0 + 경쟁도 점수화/선별
  report/        종합 보고서 + LLM 투자 의견서(memo.ts) + 발품 체크리스트
  legal/         법제처 법령 RAG 인제스트 + 하이브리드 검색
  run.ts         분석 오케스트레이터(점수 패스 → 의견서 2차 패스)
  eval/          모의경매 정답↔엔진 채점(평가셋) + 사례 라이브러리
shared/          공용 도메인 타입 + DB 접근 (node-postgres)
db/              자체호스팅 PostgreSQL 스키마 (db/schema.sql)
server/          Spring Boot 백엔드 (REST API + JdbcTemplate + @Scheduled + 작업 트리거)
web/             대시보드 (Vite + React 19 + TS) — Spring API 소비
scripts/         daily-digest(텔레그램 포맷)·crawl-health·tunnel-health·demo
deploy/          daily-parse.sh (systemd 타이머가 매일 실행)
docs/crawl-proxy.md  집-IP SOCKS 프록시(터널) 무인 운영 구성
```

## 아키텍처 (자체호스팅 on Oracle Cloud VM)

```
[크롤러/분석 (TS, tsx)] --writes--> [PostgreSQL+pgvector] <--reads-- [Spring Boot :8080] <-- [대시보드(React, vite preview :5174)]
        ▲ npm run crawl / analyze / digest                           ▲ @Scheduled · POST /api/jobs/* (대시보드 버튼)
systemd: gyeongmae-api.service(:8080) · gyeongmae-web.service(:5174) · gyeongmae-parse.timer(06:00 KST → deploy/daily-parse.sh)
```

Spring Boot가 API·작업 트리거를 담당하고, 검증된 TS 크롤러/권리분석 엔진을 그대로 재사용(같은 Postgres에 적재). Supabase·Vercel 의존 제거.

## 무인 운영

- **일일 배치**: `gyeongmae-parse.timer`(매일 06:00 KST) → `deploy/daily-parse.sh`:
  `법원경매 크롤(--source=courtauction, 메인) → analyze --all(권리·입지·점수 + LLM 의견서 2차 패스) → 수집 헬스체크 → 다이제스트 → 텔레그램 발송`.
  크롤이 실패해도(차단 등) 분석은 DB·캐시 기반으로 계속 진행.
  수집 도중 IP 차단으로 끊기면 그때까지 저장한 건수와 함께 `gm_crawl_runs.status='blocked'`로 남기고 종료 코드 1을 돌려, 일부만 받은 날도 "경매 크롤 실패" 알림이 간다.
- **크롤 IP**: VM(데이터센터) IP는 차단되므로 **집 IP SOCKS 프록시**(`CRAWL_PROXY`, `ssh -R` 역터널) 경유. 구성·예방은 `docs/crawl-proxy.md`.
  - ⚠️ 더낙찰옥션 차단은 **계정 단위**(데이터센터 IP 로그인이 트리거) — 법원경매를 메인으로 운용.
- **법원 커버리지**: 기본 본원 9곳(서울 5·의정부·인천·수원·성남지원). 서울은 전부, **경기는 본원만** — 지원(여주·평택·안산·안양·고양·남양주·부천)은 미포함.
  확장: `npm run discover:courts`(VM에서 실제 코드→지역 검증) → `COURT_EXTRA=B000252:여주지원,…`를 `.env`에 추가하면 다음 크롤부터 수집·결과폴링 대상에 포함.
- **LLM 비용**: 의견서·2차 검증·복기는 **Claude Max 구독 CLI**(`claude -p`) 사용 → 종량제 API 회피. 호출 인자는 `shared/claude-cli.ts` 한 곳에 둔다 — 기본값으로 부르면 Claude Code 시스템 프롬프트·도구 정의가 실려 호출당 입력이 약 4.8만 토큰이고, 이를 끄면 의견서 1건이 약 1,700 토큰이다(2026-11 실측). 등기 미확보 1차 소견은 규칙 판정이라 LLM을 부르지 않는다.
  배치 버스트 레이트리밋 대비 throttle + 백오프 재시도 + 입력 해시 캐시 적용(`MEMO`, `MEMO_TOP_N`, `MEMO_THROTTLE_MS`).
- **알림**: 수집 굶음(0건)·크롤 차단·터널 다운·일일 추천을 텔레그램으로 — **경매 전용 봇** `scripts/notify-telegram.sh`
  (`GM_TELEGRAM_BOT_TOKEN`·`GM_TELEGRAM_CHAT_ID`, 미설정 시 기존 `.hermes` 봇 폴백).

## 빠른 시작

```bash
# 1) 의존성 (이미 설치됨)
npm install && (cd web && npm install)

# 2) PostgreSQL + pgvector (이미 이 VM에 설치·DB생성 완료)
#    재설정이 필요하면: psql -d gyeongmae -f db/schema.sql

# 3) 환경변수
cp .env.example .env            # DATABASE_URL · 카카오/국토부/법제처 키 · CRAWL_PROXY(집-IP 터널)
cp web/.env.example web/.env    # (로컬 dev/preview는 /api 를 :8080 으로 프록시)

# 4) 엔진 시연 (키/DB 불필요)
npx tsx scripts/demo.ts

# 5) 테스트 / 타입체크
npm test && npm run typecheck

# 6) Spring 백엔드 (운영은 systemctl, 로컬은 run.sh)
bash server/run.sh                                  # :8080

# 7) 크롤 → 분석
npm run crawl -- --source=courtauction              # 법원경매(메인) 수집 → Postgres
npm run analyze -- --all                            # 권리·입지·점수 + 의견서 → Postgres
MEMO=off npm run analyze                            # 의견서 생략(신규만 빠른 분석)
npm run digest                                      # 다이제스트 텍스트 미리보기(stdout, 발송 X)

# 8) 대시보드
cd web && npm run preview                           # :5174 → Spring API 소비
```

## 데이터 흐름

크롤러(법원경매) → `gm_listings`/`gm_listing_docs` → 분석 파이프라인
(권리 rule engine → 입지 API → 진짜안전마진·경쟁도 점수 → 종합 보고서 → 통과 상위 LLM 의견서)
→ `gm_rights_analysis`/`gm_location_analysis`/`gm_scores` → Spring API → 대시보드/다이제스트.
법령 RAG(`gm_legal_chunks`)는 Claude 검증의 인용 grounding.

### 추천 순위 검증 (운영 추천과 분리)

`npm run ml:weekly`는 D-1·D-7에 동결한 비교 후보군(추천·조건부 중 신뢰·권리·입찰 범위 게이트 통과)으로 [주간 순위 복기](docs/phase2/ml-plan.md)를 만든다. 결과는 `artifacts/ml/weekly-shortlist.md`. 현행 정밀은 그중 숏리스트 매물만, 권장 입찰가 기준 예상 순마진율과 섀도 모델은 후보군 전체에서 주 7건 한도로 고른다. 목표 충족은 매각 후 180일 같은 건물·같은 평형 실거래 시세(`gm_post_sale_values`, `ml:avm`이 기록)로 판정하므로 약 7개월 뒤 확정되며, 그 전에는 낙찰 가능·사후 확인 대기로 표시한다. 후보 사건이 7건 이하인 주는 '순서 비교 불가'로 표시한다. 결과가 없거나 모델이 기권하면 그 사실을 그대로 표시한다. 입찰가·권리 게이트·텔레그램 추천은 변경하지 않는다.

## 외부 시세·공시 (k-skill)

분석에 빈 칸만 채운다. 이미 있는 법원 크롤·더낙찰 공시가격·자체 MOLIT 키는 그대로 1순위다.

| 붙인 것 | 쓰는 곳 |
|---|---|
| `real-estate-search` | MOLIT 키 없음·쿼터·장애 시 실거래/전월세 폴백. 단독·상업은 이 경로만 |
| `housing-official-price` | 공동주택·개별주택 공시가격이 없을 때 채권 기준. 후보·동·호가 여러 개면 고르지 않음. 공동주택은 VWorld 공동주택가격(`VWORLD_KEY`, 필지+호)을 먼저 보고, 없거나 하나로 못 좁히면 이 경로 |
| `gongsijiga-search` | 토지·단독·상업의 개별공시지가(원/㎡). 시세로 쓰지 않고 주택 공시가격으로 바꾸지도 않음 |
| `building-register-search` | 표제부(주용도·층·사용승인)가 없을 때. 자체 키로 data.go.kr 건축HUB(`BldRgstHubService`)를 먼저 부르고, 키가 없거나 그 호출이 실패하면 이 경로 |

안 붙인 것: `court-auction-notice-search`는 기존 법원 크롤러와 같은 사이트라 이중 호출이 IP 차단을 부른다. `lh-notice-search`·`sh-notice-search`는 청약 공고라 경매 의사결정 입력이 아니다. `daangn-realty-search`는 호가라 실거래 시세와 섞지 않는다.

끄기: `KSKILL_MOLIT_FALLBACK=off`, `KSKILL_ENRICH=off`.

자체 키(`MOLIT_SERVICE_KEY`)는 data.go.kr 계정 키라 API마다 활용신청이 따로 필요하다. 승인된 것: 아파트·연립다세대·오피스텔 매매와 전월세, 건축HUB 건축물대장(오피스텔 매매·건축물대장은 2026-11-18 승인, 만료 2028-11-18). 단독·상업 실거래는 공식 응답의 지번이 `1***`로 가려져 있어 프록시 경로를 그대로 둔다.

자체 MOLIT 조회는 1,000행씩 `totalCount`까지 넘겨 받는다(최대 10쪽). k-skill 프록시는 쪽 넘김이 없어 1,000행에서 끊기므로, 거래가 많은 시군구·월을 폴백으로만 받으면 표본이 일부만 들어온다.
시군구 코드를 주소 표에서 못 찾으면(개편된 행정구역 등) 지오코딩 캐시의 PNU 앞 5자리로 보완한다.

시세 추정(`estimateMarketPrice`)은 비교군을 좁은 순서로 고른다. 같은 건물은 법정동이 같고 지번이 같은 거래로 찾는다(실거래에 지번이 없으면 건물명 앞부분). 법원 대표지번이 '146-18외 1필지' 꼴이면 앞의 지번만 쓰고, 블록 이름이면 지번이 없는 것으로 본다. 오피스텔 매매는 2026-11 활용신청 승인 뒤 공식 API로 받아 지번·해제 여부가 들어온다(그 전 k-skill 프록시 자료에는 지번이 없었다). 지난 경매 오피스텔 355건으로 견주면 같은 건물을 찾은 물건이 254 → 283건, 20% 넘게 빗나간 비율이 13.6% → 10.7%였다. 오피스텔은 그 지번에 거래가 한 건도 없으면 이름이 똑같은 거래를 같은 건물로 쓰고 신뢰도는 medium 까지만 준다(지번 거래를 빼고 맞혀 본 141건에서 20% 넘게 빗나간 비율 19.9% → 9.2%, 빌라는 38.6% → 46.6%로 나빠져 넣지 않았다). 해제된 계약은 뺀다. 직거래는 중개거래만으로 그 단계의 최소 건수를 못 채울 때만 섞는다. 값은 ㎡당가 중앙값 × 전용면적이다.

| 순서 | 비교군 | 신뢰도 |
|---|---|---|
| 1 | 같은 건물·같은 면적(±5%), 최근 5건 | 2건 이상 high, 1건 medium |
| 2 | 같은 건물·비슷한 면적(±15%) | 2건 이상 high, 1건 medium |
| 3 | 같은 건물 전체 | medium |
| 4 | 같은 동·비슷한 면적·준공 ±5년(3건 이상일 때), 최근 20건 | medium (아파트·상가는 low) |
| 5 | 같은 동·비슷한 면적 | low |
| 6 | 같은 동 전체, 구 전체·비슷한 면적 | low |

신뢰도는 단계별 실측 오차를 따른다. 2026-07~10 실거래 한 건씩을 그 전 1년 거래로 맞혀 본 중앙 오차(20% 넘게 빗나간 비율)는 high 가 아파트 3.8%(1%)·빌라 6.1%(14%)·오피스텔 4.2%(4%), 같은 건물·같은 면적 1건이 5.4%(9%)·8.9%(23%)·5.5%(9%), 동·면적·준공 3건 이상이 빌라 14.4%(37%)·오피스텔 15.5%(39%), low 단계는 30% 안팎(60~80%)이다. 아파트는 준공연도를 맞춘 동 단위 비교군도 32.9%(64%), 상가는 17.8%(47%)라 low 로 둔다.

신뢰도가 low 인 시세는 정밀 추천의 근거로 쓰지 않는다(보류, `LOW_MARKET_CONFIDENCE`). 자료 신뢰성 검사(`INSUFFICIENT_COMPS`)는 건수가 아니라 근거의 질을 본다 — 신뢰도 medium 이상이면 비교사례가 3건 미만이어도 통과하고, low 는 3건 이상이어야 한다. 비교사례가 1건뿐이면 정밀 평가는 추천이 아니라 조건부(`SINGLE_COMPARABLE`)로 둔다. 정밀 평가의 비교사례 가격도 물건 전용면적 기준으로 환산해 견준다.

물건 종류는 법원 용도명으로 정하되, '상가,오피스텔,근린시설'처럼 세 용도를 묶은 이름이면 용도 중분류 코드(`mclsUtilCd`)가 주거용 건물(20100)이 아닐 때 상가로 본다. 이 이름이 붙은 활성 매물 1,663건 중 1,062건이 그랬고, 그 물건들은 낙찰가율 중앙값이 49%로 오피스텔(65~71%)과 다른 집단이었다.

경매 매물의 추정 시세를 매각기일 뒤 180일 안에 같은 건물·같은 면적에서 실제로 거래된 값과 비교했다(2026-11, 3,448건, 추정 시점에 볼 수 없던 거래는 제외). 중앙 절대오차율이 13.8% → 5.8%가 됐다(아파트 12.4% → 3.9%, 오피스텔 11.7% → 7.6%, 빌라 18.5% → 12.1%). 그전에는 주소에서 뽑은 단지명으로만 같은 건물을 찾아, 같은 건물 거래가 있어도 대부분 동 단위 비교군으로 떨어졌다.

추정 시세가 감정가의 3배를 넘으면 감정가 기준으로 눌러 저신뢰로, 30% 미만이면 값은 두고 저신뢰로 낮춘다.

프록시는 IP당 분당 약 180건을 넘으면 429(`retry_after_ms`)를 준다. 프록시 호출은 프로세스 안에서 `KSKILL_PROXY_INTERVAL_MS`(기본 400ms) 간격으로 줄 세우고, 429는 안내된 시간만큼 쉬었다 다시 보낸다. 간격은 프로세스별이라 프록시를 쓰는 배치(`analyze`, `ml:avm`)를 동시에 돌리지 않는다. 공시·대장 보강은 연속 3회 실패하면 5분 쉬고 다시 시도한다.

## 권리분석 엔진 (핵심)

`pipeline/rights/engine.ts` — 결정형. 우선순위/인수·소멸·대항력 **판정은 코드가** 한다(LLM 아님).
- 말소기준권리 = {근저당·저당·(가)압류·담보가등기·경매개시} 중 최선순위
- 대항력 = `max(점유, 전입)+1일 0시` ≤ 말소기준일 (익일 0시 규칙)
- 소액임차인 = **첫 담보물권 설정일** 기준 시행령 표(`sohaek-table.ts`)
- 인수금액 = 대항력 임차인 미회수 보증금 + 인수 전세권 등
- 유치권·법정지상권·대지권미등기 등 등기부 외 권리는 **레드플래그**(자동판정 X, 사람 검토)
- 법원경매는 **매각물건명세서**의 구조화 필드(임차인·최선순위설정·인수권리)로 분석
- 최선순위설정·임차인이 모두 비어 있으면 권리분석을 보류하고 `[데이터 불완전]`으로 표시한다. 원인은 셋으로 나눠 안내한다(`pipeline/report/data-gap.ts`):
  **명세서 미수집**(상세를 못 받음) · **명세서 공개 전**(매각 14일보다 일찍 받은 상세 — 명세서는 매각 임박해서야 공개된다) · **명세서 기재 없음**(공개 뒤 받았는데도 빈 경우, 등기부 직접 확인)
- 증분 크롤의 임박 재수집 예산(`--max-refresh`, 기본 250건/일)은 "공개 전에 받아 명세서가 빈 임박 물건"에 먼저 쓴다(안전마진 큰 순). 예산을 늘리면 보류가 빨리 줄지만 법원 사이트 차단 위험이 커진다.

## 대시보드 사용법

- **오늘**(첫 화면): 요약 4칸(전체·통과·오늘 기일·7일 이내) → 이번 주 기일 → 이번 주 정밀 추천 → 먼저 볼 물건 → 운영·보강 상태. 숫자와 날짜를 누르면 그 조건으로 목록이 열린다.
- **이번 주 정밀 추천**: 일반 점수 목록과 분리된 최우선 인박스. `recommended` 판정만 표시하며 0건이어도 일반 목록을 추천으로 승격하지 않음.
- **목록**: 왼쪽 메뉴(모바일은 상단 탭)에서 전체 매물 · 추천(통과 매물·점수순) · 관심 · 결정 기록 · 임장. 검색·종류·정렬·필터가 한 줄, 그 아래 **빠른 필터 칩**(오늘 기일·7일 이내·검토 권장·무피 후보…).
- **정렬**: 점수순·**진짜마진순**·**저경쟁순**·임박순·갭(소자본)순·임장 진행도순.
- **필터 > 같은 사건 묶어 보기**: 같은 사건 다물건을 1줄로 접음. **목록/지도 전환**: 마진색 핀.
- **더보기**: 조건 설정·도움말(점수 구성·통과 기준·표 읽는 법)·관심 비교·CSV·새로고침·크롤/분석 실행. 점수에 마우스를 올리면 분해(안전·권리·경쟁)가 보임.
- **행 클릭 → 상세**: 정밀 판정(말소기준권리·점유·인수금액·보수적 가치·절대 입찰상한) · 판단 기록 · AI 투자 의견서 · 권리분석 · 취득비용 · 입찰 전 체크리스트 · 원본 링크. 일반 예상가와 정밀 상한을 구분해 보여준다.
- **판단 기록**: 검토 상태, 보류/제외 사유, 임장 메모, 목표 입찰가를 저장하고 결정 이력과 복기 지표에서 다시 확인.
- **조건 설정**: 관심지역·물건종류·가격대·안전마진 기준·경쟁/권리 가중치 조정(localStorage 저장).
- **복기**: 지난 판단을 실제 낙찰 결과와 맞춰 보는 오프라인 지표.

정밀 추천의 백필·감사·기능 플래그·롤백 절차는 `docs/precision-first-operations.md`, 실제 운영 배포 검증 결과는 `docs/qa/2026-08-21-precision-first-final-qa.md`를 참고한다.
