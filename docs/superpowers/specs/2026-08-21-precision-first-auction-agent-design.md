# 정밀도 우선 경매 에이전트·대시보드 설계

## 1. 목표

현재 시스템을 “통과 매물을 많이 보여주는 검색 도구”에서 “불확실한 물건은 추천하지 않고, 검증 가능한 소수 후보만 다음 행동과 함께 제시하는 의사결정 도구”로 전환한다.

운영 목표는 다음과 같다.

- 최종 추천은 주 3~7건을 기본 상한으로 한다.
- 추천 후보의 핵심 데이터 누락을 0건으로 만든다.
- 사용자의 일일 검토 시간을 10~15분 이내로 줄인다.
- 권리·금액·물건번호가 불확실한 후보는 점수와 무관하게 `보류`한다.
- 모델은 권리 하드룰을 변경하지 못하며, 가격·선호도 판단에서도 검증된 정제 데이터만 사용한다.
- 추천·보류·제외·임장·입찰 결정과 그 이유를 축적해 일반적인 인기 매물이 아니라 사용자에게 맞는 매물을 학습한다.

## 2. 현재 기준선

2026-08-21 운영 DB 읽기 전용 점검 기준:

- 전체 매물 19,813건, 최근 7일 활성 매물 10,702건.
- 분석 완료 18,986건, 활성 통과 매물 1,450건.
- 활성 매물 중 점수·권리·입지 분석 누락 각각 788건.
- 활성 매물 중 비교사례 0건 6,339건, 통과 매물 중 비교사례 0건 635건.
- 예측 스냅샷 17,227건, 결과 행 20,647건, 낙찰가 라벨 2,600여 건.
- 지난 매각 스냅샷 결과 미매칭률 약 37%.
- 예상 낙찰가 MAPE 약 27%.
- 사용자 즐겨찾기 0건, 임장 기록이 있는 매물 3건.
- `gm_today_actions` 원천 큐는 결과복기 7천여 건, 재수집 5천여 건 등으로 사람이 처리할 수 없는 규모다.
- 감정가 대비 낙찰가율이 약 4.6배, 12배, 46배인 결과가 존재한다. 일괄매각 총액, 사건 단위 결과 혼입, 원천 오류 가능성이 있으므로 학습 전에 격리가 필요하다.

이 기준선은 구현 완료 후 같은 쿼리로 재측정한다.

## 3. 설계 원칙

### 3.1 모르면 안전이 아니라 보류

문서, 임차인, 물건번호, 시세, 낙찰결과 중 핵심 필드가 없거나 서로 충돌하면 추천하지 않는다. `null`, 파싱 실패, 오래된 문서, 비정상 단위는 모두 명시적인 보류 사유가 된다.

### 3.2 추천 판정과 순위 점수 분리

100점 점수는 이미 추천 자격을 얻은 후보의 순서를 정하는 보조값으로만 사용한다. 추천 자격은 데이터 신뢰성, 권리 안전성, 가격 근거, 손실 시나리오를 순차 통과해야 얻는다.

### 3.3 보수적 합의

최대입찰가는 단일 시세나 단일 모델이 아니라 규칙 기반 가격, 비교사례 하단값, 결과 기반 가격 하단값의 합의로 정한다. 후보 값이 충돌하면 평균을 내지 않고 보수적인 값을 사용하거나 보류한다.

### 3.4 시점 누수 금지

모든 예측과 추천은 해당 시점에 알 수 있던 데이터 스냅샷으로 재현 가능해야 한다. 이후 결과나 갱신된 시세가 과거 예측 피처에 섞이지 않게 한다.

### 3.5 사용자 행동도 학습 데이터

즐겨찾기만으로는 선호를 설명할 수 없다. 검토, 보류, 제외, 임장, 입찰, 포기 결정과 구조화된 이유를 모두 기록한다. 자동 추천보다 사용자의 명시적 결정이 우선한다.

## 4. 목표 아키텍처

```text
원천 수집
  -> 원본 보존/해시
  -> 데이터 신뢰성 검사
       -> 격리: 오류·이상치·충돌
       -> 보류: 핵심 근거 부족
       -> 통과
  -> 권리 하드 게이트
  -> 보수적 가격·비용 시나리오
  -> 정밀 추천 판정
  -> 개인 투자조건·사건 중복 제거
  -> 주간 3~7건 결정 인박스
  -> 사용자 결정/임장/입찰 로그
  -> 결과 수집·복기
  -> 정제 학습셋·오프라인 모델 검증
```

구성요소는 다음 책임으로 분리한다.

1. `data trust evaluator`: 한 매물의 원천·문서·금액·물건번호·시세·결과 신뢰도를 결정형으로 판정한다.
2. `precision evaluator`: 권리 하드 게이트와 가격·비용·근거 커버리지를 결합해 추천 상태를 만든다.
3. `shortlist builder`: 추천 자격 후보 중 사건 중복과 지역 쏠림을 제어하고 주간 상위 후보를 고른다.
4. `decision journal`: 사용자의 검토 상태와 이유, 메모, 목표 입찰가를 시점별로 저장한다.
5. `trusted outcome dataset`: 이상치·매칭 의심·시점 누수 행을 제외한 학습 가능 결과를 제공한다.
6. `decision inbox`: 오늘 해야 할 사람의 행동만 제한된 수로 보여준다.

## 5. 데이터 신뢰성 계층

### 5.1 신뢰성 판정 결과

매물별로 다음을 저장한다.

- `status`: `trusted`, `hold`, `quarantined`.
- `score`: 0~100의 근거 완성도. 추천 자격을 대신하지 않는다.
- `reasons`: 코드와 사용자 문구를 함께 가진 구조화 사유.
- `checks`: 물건번호, 금액, 문서 최신성, 임차인, 시세, 결과, 주소 일치 검사 결과.
- `evaluated_at`, `evaluator_version`, 입력 지문.

### 5.2 핵심 검사

- `(case_no, item_no, source)` 식별자 일치와 다물건 사건 교차 주입 방지.
- 한국어 금액 파싱 결과의 원문·정규화 값·단위 검증.
- 감정가, 최저가, 예상가, 낙찰가의 합리적 비율 검사.
- 매각물건명세서, 현황조사서, 등기 파싱 결과의 문서 시각과 지문 검사.
- 임차인 행의 물건번호 근거와 보증금 파싱 신뢰도 검사.
- 비교사례 개수, 거리, 면적 유사도, 거래일 최신성 검사.
- 결과 행의 사건·물건·매각일 매칭과 일괄매각 의심 검사.

### 5.3 격리 정책

아래 예시는 자동 학습 제외 대상으로 시작한다.

- `sold_amount / appraisal_value`가 0.2 미만 또는 1.5 초과.
- 다물건 사건의 한 물건에 사건 총액으로 의심되는 결과가 연결됨.
- 감정가 또는 낙찰가의 단위 신뢰도가 낮음.
- 동일 사건·물건·매각일에 서로 다른 결과가 존재함.
- 결과 수집일이 매각일보다 이르거나 미래 회차와 모순됨.

경계값은 운영 추천을 바꾸지 않는 리포트 모드에서 분포를 확인한 뒤 조정한다. 격리 행은 삭제하지 않고 사유와 함께 보존한다.

## 6. 정밀 추천 엔진

### 6.1 판정 상태

- `recommended`: 모든 필수 게이트를 통과하고 가격 근거가 충분함.
- `conditional`: 현장 확인이나 한정된 추가 문서 확인으로 해소 가능한 항목만 남음.
- `hold`: 핵심 데이터 부족, 충돌, 낮은 신뢰도.
- `rejected`: 권리·가격·수익성·투자조건을 명확히 충족하지 못함.

### 6.2 필수 게이트

`recommended`는 모두 충족해야 한다.

- 데이터 신뢰성 `trusted`.
- 인수 예상금액 0원.
- `review_required` 권리등급 없음.
- 위험 특수권리 없음.
- 점유관계 미상이 아님.
- 시세와 예상 낙찰가가 존재함.
- 비교사례 또는 충분한 결과 기반 가격 근거가 존재함.
- 보수적 최대입찰가가 현재 최저가 이상임.
- 취득세, 법무비, 명도비, 수리비, 금융·보유비, 인수금액, 불확실성 준비금 반영 후 목표 마진 충족.

### 6.3 보수적 가격

가격 후보는 다음으로 구성한다.

- 면적·거리·유형·거래시점을 반영한 실거래 비교사례 하단 추정.
- 지역×물건종류×유찰회차의 신뢰 가능한 낙찰가율 하단 추정.
- 오프라인 모델의 하단 예측 구간. 채택 게이트 통과 전에는 참고값이다.

보수적 매도가치는 신뢰 가능한 후보의 하단값을 사용한다. 후보 간 차이가 허용 범위를 넘으면 `hold`한다.

### 6.4 입찰가 두 단계

- `recommended_bid`: 목표 마진과 준비금을 충분히 남기는 권장값.
- `hard_cap_bid`: 넘으면 시스템의 투자 가정이 깨지는 절대 상한.

대시보드는 두 값의 차이와 상한을 변화시키는 민감도 요인을 함께 보여준다.

### 6.5 최종 후보 제한

- 기본 주간 5건, 설정 범위 3~7건.
- 동일 사건은 대표 1건을 우선하며 나머지는 사건 내 비교로 제공한다.
- 동일 건물·단지·주소의 사실상 중복 후보를 접는다.
- 점수가 아니라 `추천 자격 -> 근거 신뢰도 -> 보수적 마진 -> 기일 임박도` 순으로 정렬한다.
- 추천 슬롯을 채우기 위해 조건을 완화하지 않는다. 자격 후보가 2건이면 2건만 보여준다.

## 7. 결정 인박스와 대시보드

### 7.1 첫 화면

첫 화면은 전체 목록이 아니라 다음 다섯 큐를 보여준다.

- 오늘 검토할 신규 추천.
- 추가 확인 한 가지로 결론 낼 조건부 후보.
- 문서·기일·최저가가 바뀐 관심 후보.
- D-3 이내 입찰가 확정 후보.
- 결과가 나와 사용자 판단을 복기할 후보.

각 큐는 처리 가능한 상한을 가진다. 시스템 운영용 재수집·분석 실패 수천 건은 사용자 인박스와 분리해 운영 상태 화면에 집계로만 표시한다.

### 7.2 한 화면 한 결정

상세 화면의 핵심 행동은 다음으로 제한한다.

- `검토 시작`.
- `관심`.
- `조건부 보류`.
- `임장 진행`.
- `입찰 검토`.
- `제외`.

`보류`와 `제외`에는 가격, 권리, 입지, 현장, 자금, 일정, 취향, 데이터 부족의 구조화 이유를 선택한다. 자유 메모는 선택 사유를 보완한다.

### 7.3 추천 설명

추천 카드와 상세는 다음을 우선 표시한다.

- 추천 이유 3개.
- 탈락 가능 이유 3개.
- 아직 확인해야 할 항목.
- 권장 입찰가와 절대 상한.
- 상한이 변하는 민감도.
- 근거 문서·비교사례·원본 링크.
- 데이터 최신성과 신뢰도.

기존 전체 목록, 지도, 비교 기능은 탐색 보조로 유지하되 첫 동선에서 내린다.

## 8. 결정 저널과 개인화

### 8.1 이벤트 모델

사용자 결정은 덮어쓰지 않고 이벤트로 저장한다.

- 매물 식별자와 당시 사건·물건번호.
- 결정 종류와 구조화 이유.
- 당시 추천 상태, 점수, 권장가, 절대 상한.
- 사용자가 입력한 목표 입찰가와 메모.
- 결정 시각과 화면 진입 경로.

현재 상태는 최신 이벤트로 계산하고, 과거 이벤트는 개인화 학습과 복기에 사용한다.

### 8.2 개인화 순서

1. 명시적 제외 규칙과 예산·지역·물건종류를 결정형으로 반영한다.
2. 충분한 결정 로그가 쌓이면 제외 이유와 관심 전환율을 리포트한다.
3. 최소 표본과 시간분할 검증을 통과한 뒤 소프트 순위에만 개인화 가중치를 적용한다.
4. 권리 하드 게이트와 절대 입찰 상한은 개인화 모델이 바꾸지 못한다.

## 9. 축적 데이터 수명주기

### 9.1 원본층

- 원천 응답, 문서 지문, 수집 시각, 파서 버전, 출처를 보존한다.
- 재파싱 가능성을 위해 변경하지 않는다.

### 9.2 정제층

- 정규화 금액, 사건·물건 식별자, 문서 최신성, 신뢰성 판정과 사유를 저장한다.
- 오류 수정 시 이전 판정은 버전으로 추적한다.

### 9.3 학습층

- 신뢰성 `trusted`이고 결과 매칭이 확정된 시점 스냅샷만 사용한다.
- 격리·보류 행은 학습에서 제외하지만 데이터 품질 리포트에는 포함한다.
- 시간분할 백테스트와 현행 규칙 대비 성능을 함께 저장한다.

### 9.4 사진

- 매각·취하·종결 시 원본 사진 파일은 기존 정책대로 삭제한다.
- 사진 개수, 수집 시각, 콘텐츠 해시, 출처, 삭제 시각과 사유는 유지한다.
- 학습용 이미지 사용은 별도 동의와 보존 정책이 마련되기 전까지 하지 않는다.

## 10. 평가 지표

### 10.1 사용자 가치

- 일일 검토 시간.
- 주간 최종 후보 수.
- 추천에서 검토 시작으로 전환된 비율.
- 검토 후 즉시 제외된 추천 비율.
- 임장·입찰 검토까지 진행된 추천 비율.

### 10.2 정밀도

- `Precision@3`, `Precision@5`.
- 추천 후보 중 데이터 신뢰성 결함 비율.
- 추천 후보 중 권리 하드 게이트 사후 위반 비율.
- 보수적 최대입찰가 이하 낙찰 비율.
- 추천 당시 가정으로 계산한 사후 마진 분포.

### 10.3 데이터 품질

- 결과 매칭률.
- 핵심 피처 커버리지.
- 격리율과 격리 사유 분포.
- 다물건 사건 매칭 감사 통과율.
- 금액·문서·주소 충돌률.

`실현마진`은 실제 매도·임대·수리·금융비 데이터가 없으면 추정 마진으로 명명한다. 추정값을 실제 수익으로 표현하지 않는다.

## 11. 오류 처리와 안전장치

- 신뢰성 평가 실패는 기존 추천 상태를 그대로 유지하지 않고 `hold`로 내린다.
- 배치 일부 실패 시 성공 행은 저장하고 실패 행은 재시도 큐와 사유를 남긴다.
- 스키마 변경은 기존 목록 API와 점수 테이블을 즉시 제거하지 않고 병행 기간을 둔다.
- 새로운 추천 엔진은 먼저 shadow 모드로 실행해 기존 결과와 비교한다.
- 추천 수가 급증하거나 핵심 데이터 누락 추천이 발생하면 자동 승격을 중단한다.
- 운영 대시보드는 신규 정밀 추천 API 실패 시 기존 목록으로 복귀하되, 기존 점수를 정밀 추천으로 표시하지 않는다.

## 12. 구현 단계와 커밋 경계

### 단계 1. 데이터 신뢰성

- 신뢰성 판정 순수 모듈과 테스트.
- 신뢰성·격리 결과 스키마와 마이그레이션.
- 운영 데이터 백필과 품질 리포트.
- 극단 낙찰가 및 다물건 결과 학습 제외.
- 검증 후 별도 커밋·푸시.

### 단계 2. 정밀 추천 엔진

- 판정 상태와 필수 게이트.
- 보수적 가격 합의와 입찰가 두 단계.
- shadow 평가 및 추천 상한.
- 기존 점수와 비교 리포트.
- 검증 후 별도 커밋·푸시.

### 단계 3. 결정형 대시보드

- 사용자 인박스와 운영 큐 분리.
- 추천·조건부·보류·제외 설명 UI.
- 권장가·절대 상한·민감도 표시.
- 전체 목록은 보조 탐색으로 유지.
- 브라우저 QA 후 별도 커밋·푸시.

### 단계 4. 결정 저널과 개인화 기반

- 결정 이벤트 스키마와 API.
- 구조화된 보류·제외 이유 UI.
- 결정 이력과 복기 화면.
- 개인화는 리포트 및 소프트 shadow 순위까지만 적용.
- 검증 후 별도 커밋·푸시.

### 단계 5. 운영 적용과 전체 QA

- 운영 DB 마이그레이션 백업·적용·검증.
- 전체 테스트, 타입체크, 웹 빌드, Spring 테스트.
- 핵심 사용자 흐름 브라우저 검증.
- 기존 배치·텔레그램·사진 수명주기 회귀 검증.
- 프로덕션 서비스 재시작과 헬스체크.
- 최종 검수 결과 문서화 후 커밋·푸시.

## 13. 테스트 전략

### 13.1 단위 테스트

- 금액·물건번호·문서 최신성·결과 이상치 신뢰성 판정.
- 모든 추천 하드 게이트와 경계값.
- 보수적 가격 후보 충돌과 입찰 상한 계산.
- 결정 상태 전이와 구조화 이유 검증.

### 13.2 통합 테스트

- 크롤 원천부터 신뢰성·권리·가격·추천까지 고정 fixture 재생.
- 다물건 사건에서 물건별 임차인·결과 분리.
- DB 마이그레이션과 API 응답 호환성.
- 결정 이벤트 기록 후 현재 상태 계산.

### 13.3 데이터 QA

- 운영 데이터의 격리 예상 분포와 대표 샘플 수동 확인.
- 기존 극단 이상치가 학습셋에서 제외되는지 확인.
- 추천 후보에 핵심 누락이 없는지 SQL 불변조건으로 확인.
- 추천 수 상한과 사건·주소 중복 제거 확인.

### 13.4 UI QA

- 데스크톱·모바일에서 오늘 인박스 처리.
- 추천 근거와 원본 링크 접근.
- 보류·제외 이유 저장과 새로고침 후 복원.
- API 장애 시 오해를 유발하지 않는 fallback 문구 확인.

## 14. 배포와 롤백

1. 스키마를 하위 호환으로 먼저 적용한다.
2. 신뢰성·정밀 추천을 shadow 모드로 백필한다.
3. 데이터 QA 게이트를 통과한 뒤 API에 읽기 경로를 연다.
4. 대시보드는 기능 플래그로 정밀 추천 인박스를 활성화한다.
5. 24시간 운영 로그와 후보 수를 확인한 뒤 기본 화면으로 승격한다.

롤백 시 신규 기능 플래그를 끄고 기존 목록 API를 유지한다. 신규 테이블과 이벤트는 삭제하지 않으며, 원인 분석 후 재사용한다.

## 15. 완료 조건

- 데이터 신뢰성, 정밀 추천, 결정 인박스, 결정 저널이 운영 DB와 대시보드에 연결되어 있다.
- 신규 추천 후보에 핵심 데이터 누락이 없다.
- 후보 상한과 불확실성 보류 정책이 실제 API 응답에서 확인된다.
- 극단 결과 이상치가 학습·보정 통계에서 제외된다.
- 사용자 결정과 이유가 저장되고 복기 가능하다.
- 기존 권리 하드룰, 배치, 텔레그램, 사진 삭제 흐름이 회귀하지 않는다.
- 전체 테스트와 브라우저 QA가 통과한다.
- 각 단계가 독립적인 한국어 커밋으로 원격 저장소에 푸시되어 있다.
